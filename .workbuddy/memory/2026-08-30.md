## 23:30 修复：前端 403 (权限不足) / [API] http 权限不足

- 现象：点开「系统日志」页报 `console.error @ (index):[n] [API] http 权限不足`（即 `/api/logs` 返回 403 Forbidden）。Chrome Built-In AI (LanguageDetector) 提示为浏览器原生噪声，无关。
- 根因（前后端权限数据源不一致）：前端菜单可见性用 `user.role_level`（来自登录响应，存 localStorage）；后端 `RequireRoleLevel(2)` 用 JWT 的 `rl` 声明。中间件无论如何都会 `c.Set(ctxUserRoleLvl, claims.RoleLevel)`——对**早于 rl 声明存在的旧令牌**，`RoleLevel` 为零值 0，被 `GetRoleLevelFromContext` 当作合法 int 直接返回 → 后端判为级别 0 → 403；而前端仍按旧登录响应的 role_level 显示菜单（如管理员=3）。用户未重登、持有旧令牌即触发。
- 修复（两处）：
  1. 后端 `internal/api/ticket_handler.go` 的 `GetRoleLevelFromContext`：`rl==0` 视为「未携带」而回退到 `models.GetRoleLevel(role)`（admin→3）。旧管理员令牌因此恢复 200，无需强制重登。
  2. 前端 `web/index.html`：新增 `decodeRoleLevel(token)`（base64url 解 payload 读 `rl`），在「页面加载时」与 `persistSession` 中均以 JWT 的 `rl` 为权限级别权威源，缺省回退到登录响应/本地缓存的 role_level——使菜单可见性与后端门控同源。
- 验证：`go build/vet` 通过；前端内联脚本 `vm.Script` 语法校验通过；重启 8080（PID 5577）后实测：`no token→401`、旧管理员(无 rl)→200、admin(rl=3)→200、auditor(rl=2)→200、operator(rl=1)→403、只读(rl=0)→403。权限阈值精确保持 ≥2。
- 经验：`GetRoleLevelFromContext` 读取 JWT 数值声明时必须区分「0=未携带」与「0=合法最低级」，否则零值会绕过字符串回退；前端权限判断应与后端门控共用同一声明源。

## 23:54 修复：巡检记录长时间显示 running（扫描已完成却仍是 running）

- 现象：用户发现 oa.cuz.edu.cn 的定时巡检记录（23:42 触发）在 Dashboard 扫描已完成的情况下，巡检记录列表仍显示 `running`；刷新后依旧。
- 诊断（拉取 /api/inspections/records 实测）：7 条记录最终均为 success，其中 23:42 那条 completed_at=23:47:13——即 AI 分析阶段耗时约 5 分钟。根因不是永久卡死，而是**巡检 = 扫描 + AI 分析**共用单一 `running` 状态：扫描几秒完成（Dashboard 显示已完成），但 AI 阶段仍在跑，记录一直显示 `running`，造成观感不一致。另发现 `recordRepo.Update` 未持久化 `scan_job_id`（所有记录 scan_job_id 均为 none）。
- 修复：
  1. 新增状态 `InspectionStatusAnalyzing="analyzing"`（`internal/models/inspection.go`）。
  2. `internal/inspection/runner.go` 的 `execute`：扫描结果就绪后、调用 AI 前，置 `rec.Status=analyzing` 并 `recordRepo.Update` 落库——使 AI 阶段显示为「分析中」而非卡在 running。
  3. `internal/storage/inspection_repo.go` 的 `Update` 增加 `n.scan_job_id=$scan_job_id` 持久化（之前漏写）。
  4. 前端 `web/index.html`：`getStatusBadge` 加 analyzing→badge-info；`renderInspectionRecords` 用中文标签（扫描中/分析中/成功/部分成功/失败）；stats 提示加「分析中 N」。
  5. 健壮性（防重启孤儿）：`inspection_repo.go` 加 `MarkStaleRunning(maxAge, status)`（回收 running/analyzing 超阈值记录→failed），`runner.go` 加 `RecoverStaleRecords`，在 `scheduler.go` 的 `Start()` 启动时调用（参考 ScanJob 的 MarkStaleRunning 模式）。
- 验证：`go build/vet` 通过；重启 8080（PID 6048）启动正常、无僵死记录可回收；触发手动巡检并轮询，记录于 t+66s 由 `running`→`analyzing`，确认新状态流转生效（AI 约 5 分钟，之后转 success）。
- 经验：长耗时多阶段任务不要用单一 running 状态，应在阶段切换点落库中间状态，避免前端误判“卡死”；服务重启会杀掉进行中的 goroutine，任何运行中状态都需在启动时回收，否则记录永久滞留。
